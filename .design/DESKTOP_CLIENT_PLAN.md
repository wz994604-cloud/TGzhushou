# 飞机助手 Windows 客户端完整实施方案

> 版本：2026-10-06  
> 身份：桌面端架构与 UX 设计师  
> 工作目录：`C:\Users\win11\Projects\飞机助手`

## 1. 目标与边界

将当前飞机助手网页版直接包装为正式 Windows 桌面客户端，**复用现有前端页面、接口、认证、业务流程与设计系统**，不重做项目。

客户端解决桌面运行体验，不接管服务端职责：

- 保留现有聊天、活动编写、素材、用户、任务、记录、设置页面。
- 保留现有登录、权限、机器人切换、草稿、发布和定时任务行为。
- 数据库、机器人 Token、媒体存储、定时调度继续由服务端负责。
- 客户端只增加窗口、托盘、系统通知、文件选择、安装、更新、日志与桌面快捷操作。
- 不增加离线发送、本地机器人调度、本地数据库或第二套业务 API。

## 2. 技术路线

### 2.1 客户端容器

采用 **Tauri 2 + Windows WebView2** 作为桌面壳：

- 复用现有 Vite 构建产物和 `src/main.js`、`src/workbench-shell.js`、`src/style.css`。
- 使用系统 WebView2，不内置完整 Chromium，安装包和内存占用更小。
- Rust 只负责桌面能力，不承载业务逻辑。
- 前端仍通过 HTTPS 访问现有 Railway 服务。

当前项目没有现成 Electron/Tauri 配置；客户端工程应作为同一仓库中的独立 `desktop/` 外壳加入，不复制前端和服务端代码。

### 2.2 运行模式

- 开发：Vite 本地开发服务器 + Tauri dev。
- 构建：先执行现有 `npm run build`，再由 Tauri 打包 `dist`。
- 生产：客户端只连接配置的 `PUBLIC_URL`，不在用户电脑启动 Express、PostgreSQL 或 Scheduler。
- Web 版继续保留，客户端与 Web 共用同一套前端入口。

## 3. 客户端窗口结构

```text
Tauri Window
├── 自定义标题栏
│   ├── 产品标识
│   ├── 当前页面标题
│   ├── 连接状态
│   └── 最小化 / 最大化 / 关闭
└── 现有 desktop-shell
    ├── app-rail
    ├── desktop-topbar
    └── desktop-viewport
```

### 3.1 窗口默认值

- 默认尺寸：`1440 × 900`
- 最小尺寸：`1100 × 700`
- 支持最大化、缩放和系统 DPI 缩放
- 窗口位置和尺寸保存到本地客户端配置
- 不新增假 Windows 边框；标题栏只承担真实窗口操作
- 页面内容继续使用当前三栏工作台，不套第二层“浏览器窗口”视觉

### 3.2 关闭行为

- 点击关闭：默认最小化到托盘，不终止服务端任务。
- 托盘菜单提供：显示窗口、检查更新、退出客户端。
- 真正退出前，如果存在未保存草稿，只提示本地草稿仍已保留，不阻塞退出。
- 退出客户端不退出服务器端 Scheduler，已启用任务继续运行。

## 4. 现有页面复用与桌面适配

### 聊天

- 保留当前三栏：会话列表、消息区、资料区。
- 会话列表和消息区独立滚动；输入区固定在消息区底部。
- `>=1600px` 使用完整三栏；中等宽度资料区改为抽屉；窄窗口保留当前列表/聊天切换逻辑。
- 桌面客户端只调整标题栏占用高度、窗口最小宽度和 DPI 下的溢出，不改聊天业务。

### 编写活动

- 保留当前左侧编辑、右侧预览与发布配置结构。
- 右侧预览与发布区保持 sticky；窗口较窄时自动转单列。
- 底部保存、立即发布、群发、启用定时操作保持现有含义和权限。
- 长文本、附件、按钮编辑不允许横向溢出。

### 素材、用户、任务、记录、设置

- 继续使用现有页面和真实返回数据。
- 统一继承聊天样板的材质、字体、边框、按钮和状态 Token。
- 不补造历史媒体列表、用户字段、标签、备注或不存在的接口。
- 未开放能力继续显示禁用态或“即将开放”。

## 5. 桌面 UI 调整范围

只做必要的客户端适配和已确认的 UI 精修：

1. 标题栏、窗口边缘与内容区的高度关系。
2. 左侧品牌和机器人选择入口的桌面可用性。
3. 导航、卡片、输入、按钮在 100% / 125% / 150% DPI 下的可读性。
4. 三栏布局、固定区域和独立滚动的稳定性。
5. 托盘、连接状态、更新状态和系统通知的桌面表达。
6. 文件拖拽、打开文件所在目录等桌面行为。

不做：

- 不重写页面。
- 不更换品牌视觉方向。
- 不新增业务模块。
- 不把 Mini App 样式强行移植到 Windows。
- 不用本地假数据填充空状态。

## 6. 登录、连接与安全边界

### 登录

- 首次启动进入现有登录流程。
- 登录成功后由现有服务端会话机制保持登录。
- 客户端不保存机器人 Token、管理员密码或原始 Telegram 初始化数据。
- 登录过期时回到登录页，并保留未发送草稿。

### 网络状态

统一显示四种状态：

- 已连接
- 请求中
- 网络不可用
- 结果待核实

发送、发布和删除操作失败时保留原输入，不自动重试有副作用的请求。刷新类读取请求允许用户手动重试。

### 外部链接与权限

- Telegram、媒体和普通外链交给系统浏览器打开。
- WebView 只加载项目允许的服务地址。
- Rust 命令只开放窗口、托盘、通知、文件和更新能力。
- 不允许网页直接执行任意本地命令或访问任意文件路径。

## 7. 桌面原生能力

### 第一版必须实现

- 系统托盘
- 窗口最小化 / 最大化 / 关闭
- 系统 DPI 与窗口尺寸适配
- 文件选择和拖拽上传
- 系统默认浏览器打开外链
- 客户端版本信息
- 更新检查与安装
- 脱敏诊断日志导出

### 第一版统一实现但默认关闭

- 新消息通知
- 发布失败通知
- 任务完成通知

通知必须遵循真实事件，不能由轮询重复弹出；用户可在设置中关闭。

### 暂不加入

- 多窗口编辑同一活动
- 离线发送
- 本地数据库
- 本地定时发布
- 自动开机启动
- 多账号并行窗口

## 8. 本地数据规则

允许保存：

- 窗口尺寸与位置
- 客户端偏好设置
- 当前页面与机器人选择偏好
- 本地草稿
- 最近一次连接状态
- 客户端诊断日志

禁止保存：

- 机器人 Token
- 管理员密码
- 原始登录凭证
- 未脱敏 Telegram 用户数据

本地草稿必须与当前机器人隔离，沿用现有 `draftKey()` 逻辑。

## 9. 安装、更新与版本

### 安装包

- 生成 Windows x64 安装包。
- 安装器创建开始菜单和桌面快捷方式。
- 卸载时保留或删除本地草稿、日志由用户明确选择。
- WebView2 运行时缺失时给出安装提示，不静默失败。

### 更新

- 客户端启动后检查更新，但不阻塞登录和页面加载。
- 有新版本时显示版本号、更新说明和“稍后处理”。
- 下载失败不影响当前版本继续使用。
- 更新安装前关闭当前客户端，更新失败能够回到旧版本。
- 更新包必须与当前签名和版本通道匹配。

## 10. 日志与诊断

日志分层：

- `info`：启动、登录成功、页面切换、更新状态
- `warn`：网络重连、资源加载失败、结果待核实
- `error`：客户端壳错误、更新失败、文件操作失败

日志要求：

- 自动脱敏 Token、Cookie、密码、Telegram 初始化数据和用户消息内容。
- 提供“导出诊断信息”按钮。
- 导出的内容只包含客户端版本、系统版本、时间、错误码和脱敏堆栈。

## 11. 项目文件规划

### 新增客户端外壳

```text
desktop/
├── src-tauri/
│   ├── src/main.rs
│   ├── tauri.conf.json
│   ├── capabilities/
│   └── icons/
├── updater/
└── README.md
```

### 前端最小调整范围

- `src/main.js`：仅接入客户端连接状态、通知和桌面文件行为。
- `src/workbench-shell.js`：仅接入标题栏高度、窗口状态和桌面导航行为。
- `src/style.css`：补充客户端环境下的标题栏、DPI、滚动和窗口最小尺寸规则。
- `src/desktop-bridge.js`：统一封装前端到 Tauri 的调用；Web 环境提供空实现或浏览器回退。
- `package.json`：增加桌面开发、构建和打包脚本。
- `desktop/README.md`：记录本地开发、签名、打包和更新流程。

禁止在业务文件中散落 Tauri 原生调用；所有桌面能力必须经过 `desktop-bridge.js`。

## 12. 一次性实施顺序

### 阶段 A：壳与构建

- 初始化 Tauri 2 壳。
- 接入现有 Vite `dist`。
- 验证 Windows WebView2 加载、窗口尺寸和关闭行为。

### 阶段 B：现有页面桌面适配

- 接入标题栏和窗口状态。
- 统一六个功能页面的 Token 和可见状态。
- 修正 DPI、长文本、滚动和固定操作区问题。
- 不改 API 和业务流程。

### 阶段 C：原生能力

- 托盘、通知、文件拖拽、外链打开。
- 连接状态和待核实状态。
- 日志导出与诊断信息。

### 阶段 D：发布能力

- Windows 安装包。
- 版本信息与更新检查。
- 签名、升级、卸载和回滚验证。

### 阶段 E：完整验收

- 页面功能验收。
- 网络异常验收。
- 安装升级验收。

## 13. 验收标准

### 功能

- [ ] 登录、退出、会话过期符合现有 Web 行为。

## 14. 开发者交接规则

开发者只在用户确认本方案后开始实现：

1. 先建立 `desktop/` 壳，不先重构业务前端。
2. 先完成“客户端启动 → 登录 → 聊天”闭环。
3. 再接入窗口、托盘、通知、文件和更新。
4. 每个阶段只验证受影响范围。
5. 不修改 `server/` 的业务、数据库、认证和调度逻辑。
6. 不部署 Railway，不合并 `main`，除非用户另行确认。

## 15. 当前结论

本项目适合做成正式 Windows 客户端，但正确方式是：

> **Tauri 2 桌面壳 + 现有 Vite 前端 + 现有 Railway 服务端。**

这是一套客户端化工程，不是新项目；UI 只做桌面适配和已确认的细节精修，业务功能和服务端边界保持不变。

本文件完成后等待用户确认，再交给开发者实现。
