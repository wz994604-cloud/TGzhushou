> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在现有 Vite + Telegram Mini App 中，按 `ios_swiftui_开发方案.md` 的页面结构和交互目标实现 Web 版 iOS 风格工作台，不新增 SwiftUI 工程、不改后端协议。

**Architecture:** 复用现有 `workbench-shell.js` 的 DOM 重排、`main.js` 的网络与状态逻辑、`api-client.js` 的鉴权请求和 `mini-ios-glass.css` 的视觉基础。将 SwiftUI 专属概念转换为原生 Web 等效物：NavigationStack → 页面状态与返回按钮，Sheet/Alert → 现有弹层和确认交互，SF Symbols → 现有 SVG 图标映射，Dynamic Type → `rem`/系统字体和可缩放布局。

**Tech Stack:** Vite、原生 JavaScript、CSS、Telegram WebApp、现有 Express/Serverless API。

## Global Constraints

- 只改现有 Web/Mini App；不创建 SwiftUI 工程，不更换技术栈。
- 保持 Telegram WebApp 初始化、身份头、机器人切换、现有 API 路径和后端业务规则不变。
- Mini App 主导航固定五项：聊天、编写、素材、任务、设置；用户与发布记录归入设置/更多或任务详情，不新增底部 Tab。
- 复用已有组件、网络层、模型和状态；不新增依赖。
- 页面支持浅色/深色、键盘避让、44px 触控目标、idle/loading/success/empty/failure/retry 状态。
- 修改前保留并校验现有工作树；不 reset、clean、stash、部署或推送。

## Review Focus

- 五项导航与现有 `players`/`logs` 页面映射不一致：测试导航入口、返回路径和深链接恢复行为。
- 编写五步流程的下一步/上一步、草稿恢复和预览发布：测试每一步真实表单仍绑定原事件。
- Chat composer 在键盘和安全区变化时不能遮挡：测试 `visualViewport` 更新和小屏高度。
- API 失败或切换机器人期间不能把旧数据写入新机器人：保留并验证现有 context/revision 防护。
- 任务停止/删除等危险操作必须可确认、可恢复：验证 Alert/确认交互和失败重试。
